# Writing the spec and directing the film

Part of the mechanism skill (SKILL.md). Open it while writing `spec.js` (step 3) and before rendering (steps 5 and 7): the parts library, what the director builds, looks, engines, lengths, software objects, provenance per dimension, scanned sources, encoders and brand identity.

What the director builds by itself: staggered assembly from back to front, a cutaway (parts marked `cutaway` fade) while the mechanism runs, one mode of operation at a time with its measured ratio, its published number and a live rpm readout, the exploded view, a tour with a callout per part, re-assembly, a ratios table, an evidence table with sources, and a sources panel. Sound follows the physics: each part's impact uses its material and size, and the tooth ticks are the real tooth passes of the running gears.

**One tooth count per body.** In a gear train a `body` has a single tooth count: two gears of different size on one shaft each need their own `body`, joined by a link `{ t: 'same', a: '<body>', b: '<body>' }`. The gate fails with that advice when a body mixes tooth counts. Parts library (`kit/parts.js`, real dimensions): `gear` (involute, module, teeth, pressure angle, backlash, lightening web), `ring` (internal teeth), `sprocket` (chain pitch and roller), `shaft`, `pin`, `disc`, `flange` (spoke holes), `tube`, `plate` (`holes`: `[x, y, r]` round or `[x, y, width, height]` rectangular), `profile` (`pts` outline, `holes`: a list of polygons cut out of it, so no zero-width bridges), `bearing` (balls and cage), `spring` (helix), `nut`, `bolt`. Also `box` (hollow housing with optional floor), `block` and `cross` (stem). Engine parts: `crankshaft` (throws at any angle), `conrod`, `piston` (ring grooves, compression height), `engblock` (block, head or pan with through bores), `camshaft`, `valve`. Puzzle part: `cubie` (a cube with stickers). Two kinds of mechanism: **gear trains** (`mechanism.links` + `drive.modes` with the published ratio) and **presses** (`mechanism.press = { travel, actuation, force: [[mm, cN], ...] }` + `drive.modes` as phases `{ from, to }`; parts take `slide: { k }` to follow the stroke and `compress: { free }` for springs; the director plots the force curve against what a linear spring through the first two points would give, and the gate demands a `press.note` when the published points do not add up). `up: 'z'` stands the object on its z axis (switches, towers). `orient: [rx, ry, rz]` (degrees) turns the whole object (the Enigma stack lies along x). **Engines**: `mechanism.engine = { cylinders, bore, stroke, rod, deck, ch, pitch, throws, firing, valves: { intake: { open, close, lift }, exhaust: {...} } }` is a crank-slider with the exact kinematics (piston height r cos a + sqrt(l^2 - r^2 sin^2 a)); parts take `engine: { role: 'crank' | 'cam' | 'piston' | 'rod' | 'valve', cyl, valve }` and move with it. The gate computes the displacement from the bore and stroke, demands that the published firing order is possible with the crank throws (1-2-3-4 fails on a flat-plane four) and that the piston crown reaches the deck. Cam lobes are placed from the valve windows. `late: true` makes a part arrive last (shells) and `cutaway: 0.8` sets how transparent it gets while running. **Calculated numbers**: `mechanism.calc = { vars: { name: { v, label, unit, claim } } }` with `drive.modes` of `{ expr, unit, digits, formula, publish: { value, tol, claim }, show: [part ids] }` evaluates each published figure that comes out of others (TFLOPS = cores x 2 x clock, bandwidth = bus x data rate / 8) from variables that each carry their own claim, so an estimated assumption is drawn in a different colour; parts take `spin: rad/s` (fans) and the kinds `fan` and `fins` exist. This is the cheap route for any product whose datasheet publishes derived figures (GPUs, CPUs, drives). **Puzzles**: `mechanism.cube = { pieces, pitch }` runs the Rubik cube as 26 cubies that really turn (`kit/cube.js`, no tables); modes take `alg`, `repeat`, `back` and a `metric` (`order`, `superflip`, `positions`) that the gate compares with the published number. **Ciphers**: `mechanism.enigma = { rotors, reflector, rings, start, plugs, tests: [...] }` runs the real machine logic (`kit/enigma.js`); every published test (`plain` -> `expect`, or the sequence of `windows`, or `decrypt: true` for reciprocity) is simulated and the spec fails if the machine disagrees. Parts of kind `rotor` take `role: 'R' | 'M' | 'L' | 'UKW' | 'ETW'` and get their wiring and notch from the machine config, so what is drawn is what is computed. `drive.modes` become typed phases (`start`, `text` or `'@prev'`, `publish: { text, windows }`); the film shows the rotor windows, the lampboard and the signal path through the contacts, and the viewer lets you type on the keyboard. `director.views` merges partial views (`{ iso: { yaw, pitch } }`) onto the defaults. Kinematics (`kit/kin.js`): one-degree-of-freedom gear trains by the Willis relations, external and internal meshes, carriers, fixed members, tooth phase solved so the teeth really interleave (residual reported), centre-distance and assembly checks.

**Look.** The signature look is `dossier` (blueprint grid, ruler, monospaced type, a data block counting SPEC / DERIVED / ESTIMATED): it is the default, and a film should keep it so mechanism does not look like every other explainer. Three alternatives live in `MX.styles` (`kit/core.js`): `paper`, `night` and `studio` (black set with the maker's accent). Choose with `--style` on render or `?style=` on a viewer, or `style: 'studio'` in the spec; `brand: { accent: '#76b900' }` gives the studio look its colour. A style is one table entry (palette, title font, card layout, stage: background, grid, shadow, bloom, rim light). Use `--draft` for a fast preview render.

**Presentation methods.** When requested, select `--method studio|workflow|paper` independently of `--background graphite|blueprint|porcelain|ivory` (all twelve combinations). Studio names the normal 3D director; Workflow follows actual `mechanism.steps.label(i)` data, or the drive modes in their declared order; Paper explains the tour parts using real mesh edges/silhouettes, numbered callouts and projected detail views. The same options work as URL parameters or `presentation: { method, background }` in the spec. Do not confuse the legacy `--style paper|studio` palettes with the new methods. No method/background option means the existing film is preserved. With `?explore`, only the new background is applied to the existing viewer.

**Independent engines, not palette variants.** Studio uses the product WebGL renderer (1.5x supersampling, `stage.renderScale` range 1–2). Workflow draws its own Canvas2D process scene without building the Studio object: with `workflowScene: { kind: 'reconcile', before, after, updated }` (see `examples/react`) it shows the real page, the state, both trees, the node-by-node comparison and the one DOM change; otherwise a line of stations with a carrier. Paper draws vector sheets without shaded images, lighting or shadows (flat material colour coding is allowed, as on a coloured drafting sheet): with `paperScene: { kind: 'pin-section', ... }` (see `examples/lock`) a side section driven by the published table; with `paperScene: { kind: 'geometry' }` and parts of `kind: 'drawing'` (Draft 0.2, see `docs/draft-geometry.md` and `examples/demo-*`) a dimensioned piece drawing of flat parts declared as 2D geometry, checked by the gate through `kit/geom2d.js` (Studio refuses such parts: they have no 3D model); otherwise orthographic sheets from the model meshes, used as data. Neither 2D engine may create a WebGL context or composite Studio frames. Which kit modules each engine needs is declared once in `kit/manifest.js`, read by `boot.js`, `scripts/new.mjs` and `tests/manifest.test.mjs`. `boot.js` decides the engine just before the compiler, from the URL or else `spec.presentation`, so Workflow (either way) loads no 3D code at all (no three.js, `gl.js`, `figure.js`, `parts.js`, `paper-engine.js` or `paper-mesh.js`) and Flow runs without the 3D stack. Paper is two modules: `paper-engine.js` draws (no three.js) and `paper-mesh.js` turns the compiled meshes into the plain view set it draws. A spec whose `paperScene.kind` is one Paper draws natively (`kit/manifest.js` `paperScenes`, today `pin-section`) goes straight to `paper-engine.js`: no three.js, no 3D figure, no mesh adapter; any other spec (or an unknown kind) uses the meshes. The gate runs the same either way (it reads the spec, not the meshes). The preflight's `GEOMETRY_AREA_MISMATCH` runs only where meshes are compiled (Studio, Paper without a vector scene). Where none are compiled (Workflow, Paper with a vector scene, `--skip shape`) the page publishes `window.__checks.geometryArea = { run: false, reason }` and the preflight prints `NOT RUN  GEOMETRY_AREA  <reason>` (in `--json`: `notRun`); that is neither a finding nor a pass, so check the model's flat parts with a Studio preflight. A check that throws, or an omission the engine does not explain, is `GEOMETRY_AREA_NOT_RUN` (FAIL); a page that does not report it at all (hand-built) is `GEOMETRY_AREA_UNREPORTED` (WARN). A new kit module must be added to the manifest or the manifest test fails. Motion in both uses `P.motion` (`kit/presentation.js`: closed-form spring, expo, log-space zoom, masked word rise), all pure functions of time. Studio exports STL/GLB; the 2D engines export films/stills. Studio has the orbit viewer; Workflow/Paper retain their own playback canvas with `?explore`.

Use `--length short --aspect 9:16` first: Workflow/Paper are 30 seconds (normal 60, extended 90); Studio keeps its duration. The 2D engines use CPU Canvas2D and deterministic time-based state, not temporal blur. A station's progress is illustrative, not measured latency. Changing appearance never changes the evidence verdict. Paper views are not to scale; displayed numeric parameters must already be backed by the spec. Estimates stay marked/dashed. Inspect first/middle/final frames of every step/detail and run preflight with matching method/background/length/aspect. Camera checks are inapplicable to 2D scenes; text checks and Paper's geometry-area checks still apply. Run `node --test tests/presentation.test.mjs tests/paper.test.mjs tests/paper-contract.test.mjs` after engine changes: they reject WebGL creation in Workflow/Paper, and any gradient, shadow, filter or lighting blend in a Paper frame (Paper is strokes, hatching and flat fills).

**Software.** The object can be software. Pick what the program writes or computes (a file format, a message, a result), make the real tool produce a sample, write a pure model in `kit/` from the published description, and let the spec ask the model for numbers the tool itself wrote: CRCs, sizes, and above all `rebuild the whole sample byte for byte` and `have the real tool accept what the model built`. Keep the evidence next to the spec in `data.js` (written by a script that runs the tool, so anyone can reproduce it); `check-spec.mjs` loads it. Calculated values may be strings (hex, bytes): `mechanism.calc` compares them to `publish.text`. See `examples/lock` (a pin tumbler lock with a KW1 key: the published table is cross-checked, the right key aligns every split on the shear line and a wrong key does not; `kind: profile` draws the key from a polygon, `motion(step, t, phase)` animates a "what if" phase), `examples/winrar` (software doing its job: a DEFLATE stream WinRAR wrote, unpacked token by token by `kit/deflate.js`, written from RFC 1951; the books and belt are the icon), `examples/rar5` and `kit/rar5.js`.

**Explain what it is first.** Someone who has never heard of the object has to understand what it is and what it does in the first seconds, with no help. Put its name on screen (a nameplate, or the object's own printed text), say in plain words what they are looking at (`director.what`, the step labels and the mode formulas), and use no internal jargon without explaining it. Answer the question a newcomer would ask ("what does a click do to the page?"), not the most interesting internal detail ("which list items does the reconciler move?"): keep the detail for a second film. For software, show the real input (the code on a card), the state before and after, and the real output. The stranger test is the check: if the judges describe a generic diagram instead of naming the thing, the film does not explain it yet, so rewrite the captions and the scene and test again. `examples/react` went from "a tile-sorting puzzle" (55 %, not React) to "a React 18 explainer" (90 %) with exactly that change.

**Closing card.** Every film ends on a card with the object name and the gate verdict, and nothing about this toolkit: no name, no URL, no credit. Sign it yourself if you want to with `director.outro: { title, sub, what, line, url }` (all optional), or drop the card with `director.outro: false`.

**Lengths.** Render the short cut (`--length short`, about 30 s) for sharing, the normal one for the full argument and `--length extended` when someone wants the whole teardown. Name the files `<name>-short.mp4` / `<name>.mp4`. Choose what the short cut keeps with `director.short: { modes: [ids], tour: [ids] }` (the steps phase and the first published checks by default). In the normal and extended cuts the whole exploded object is held still for `director.explodedHold` seconds (0.9 by default) before the camera flies to the first part; the short cut has no hold.

**Provenance per dimension.** When a part mixes sourced and estimated sizes, add `params: { w: { value, unit, conf, claim, tol }, wall: { conf: 'estimated', why } }`: the gate compares each drawn size with its source value and reports the part as mixed, and the card shows each size with its class. (`node scripts/registry.mjs` refreshes the register of the skill's own examples; it is for contributors, not for your object.)

Confidence is not size verification: cards explicitly say `SIZE NOT COMPARED` or how many numeric dimensions have a sourced comparator. The register records both compared and unchecked dimensions per part. Read warnings for displayed calculations with no published comparator, tooth counts outside the kinematic train, and unknown spec/part keys. A warning discloses an untested quantity; it does not prove that quantity wrong. Keep the existing VERIFIED/CONSISTENT rules, including the independent-source requirement, and never invent a comparator to remove a warning.

**Sources that are scans.** A primary source (a standard, a datasheet) can be a PDF with no text layer. Do not skip it and do not quote it from memory: render its pages to images (`uv run --with pymupdf python -c "import fitz; d = fitz.open('C:/path/file.pdf'); d[0].get_pixmap(dpi=130).save('C:/path/page-0.png')"`, with `C:/...` paths: Python on Windows rejects `/c/...`), open the images and read the numbers off them. Say in the source note that it was read by eye from page images (a digit can be misread), cross-check each figure against a second source or a computed relation, and say which reading you followed when the drawing and the printed value disagree.

**Encoders.** `--encoder browser` uses software WebCodecs H.264, with automatic JPEG fallback when unsupported; `--encoder jpeg` is the compatibility default. Do not select hardware encoding without a quality comparison. The bitrate scales with dimensions, fps and part count; override with `--bitrate <bits/s>` only after comparing the thin text in every panel. Both pipelines use limited-range BT.709 output with sRGB transfer metadata. A frame/operation stalled for 30 seconds is stopped by its owned browser PID tree and retried once; `--timeout <seconds>` adjusts the render watchdog. Browser tools allocate port zero, so `CDP_PORT` is obsolete. Render validation belongs in the user's work folder, never in `docs/media`.

**Verdict first.** `director.cold: { question, dur }` opens the film with the question and the published answers being checked row by row (the gate's own comparisons), every part's card shows its source and fetch date, and the film ends with a receipt panel (VERIFIED or DOES NOT PASS). Prefer it for any object whose point is a number someone could doubt.

**Brand identity.** An object has to look like itself: the maker's wordmark, its colours, where it is printed. Record the livery as a claim (SPEC when an opened source shows it, otherwise ESTIMATED with the reason) and draw it with `decals` on the part's faces: `decals: [{ face: '+z', at: [x, y, z], w, h, rot, glow, items: [{ t: 'text', s: 'HONDA', size, weight, spacing, color }, { t: 'rect' | 'circle' | 'line', ... }] }]`. Use type and colour only, never logo files. Parts also take `rot: [rx, ry, rz]` (degrees) and the livery materials `graphite`, `honda-red`, `nv-green`. Give the finished object a beauty shot before it is opened with `director.hold` (seconds): the assembled, lettered object turns slowly, then the cutaway starts.
